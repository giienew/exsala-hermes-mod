# Web Account Farming (HTTP mode)

## When to Use
- Farming accounts on a web app (signup + session/token extraction) without a real browser
- Target uses modern anti-bot: Cloudflare Turnstile, Castle, better-auth, Next.js Server Actions
- Need to reverse the site's real auth flow from webpack/Next.js chunks before automating it
- Wiring temp-email OTP + local captcha solver + proxy pool into an HTTP farm
- Probing an LLM inference site for a NO-AUTH guest key mint before building any signup/browser farm (Dahl-class targets) — `references/dahl-guest-key-farm.md`
- Benchmarking a farmed provider's real capacity (latency/RPM/TPS/concurrency) BEFORE mass-minting keys or wiring it into a router — the owner's standing rule; "Tes N" / "N worker M rpm" commands mean run the stress test with those parameters NOW — `references/provider-benchmark-harness.md`
- Automating a mainland-China PHONE signup (SMS OTP): Tencent 天御 click-chars captcha + nested Aliyun WAF slider — `references/cn-phone-signup-captcha.md`
- Mapping a new-api/Veloera-family AI gateway before any signup attempt (gate map, wall order, adoption-vs-farm decision) — `references/new-api-family-recon.md`
- The target provider may already have one of OUR registrar/farm repos — check `gh repo list` and memory BEFORE writing new farm code; clone + run the proven registrar, it beats re-reversing the signup flow from scratch
- Farming Crusoe Cloud (signup → OTP → API key, Playwright-based) — our `crusoe-cli` repo at `/opt/crusoe-cli`, wired to the local solver, Mailoka inbox and the proxy-pool rotator — `references/crusoe-cli-farm.md`
- Farming Oxylabs dashboard accounts (register → activate → residential-proxy asset, Camoufox legs) — the working-dir scripts, proxy-credential source, gmaildot-to-real-inbox activation, and the CF egress-ASN rule — `references/oxylabs-dashboard-farm.md`. Report VERIFIED accounts only; a run that produced zero is zero — say so plainly, never frame under-reporting as success and never blame the farm when the truth is no output. The account count IS the report; keep status honest under operational pressure. Full working flow lives in the dedicated `oxylabs-farm` skill.

Farm accounts on modern web apps without a browser: HTTP client (curl_cffi impersonation) + temp-email OTP + local captcha solver + geo-matched proxy pool (indie sites often geo-fence: a timeout/403 from the VPS just means the exit IP is foreign — probe via pool `/next?cc=<site's country>` before concluding the site is down). Registration and sign-in are TWO separate walls — a successful signup does NOT yield a session; plan the sign-in path before writing the signup code. The asymmetry runs the other way too: a "Sign up with Google/GitHub" button usually routes to the same OAuth LOGIN flow as the normal login button, and that flow rejects identities with no pre-existing account ('You are not authorized to access this application') — social sign-up is NOT a signup path. Provision via the email form first; social login only re-enters an account that already exists. A third wall can sit between them: email verification (`verification_required` in the signup response) — plan the inbox-poll AND the resend endpoint (usually turnstile-gated like the signup itself) before declaring the farm working; the signup response JSON is the gate list, read it every time. Grep the signup address's domain against a public disposable-domain blocklist BEFORE registering — a blocklist-dropping target answers 200 on signup AND on resend while no mail ever arrives (check + smtplib discriminator in `references/temp-email-providers.md`) — and probe login once to separate a credential bug from the gate (401 invalid-credentials vs 403 correct-but-unverified on strict stacks) while the poll runs. **Probe for a no-auth key-mint endpoint BEFORE building any signup/browser farm.** Many inference gateways expose a guest mint (a `POST /tokens`-style route with an empty body, no cookie, no fingerprint) that returns a full-quota bearer key — when it exists, the whole signup wall (429s, 1-account-1-browser+fingerprint, claim UIs) is moot and days of browser reversal are wasted; one curl answers it. On such gateways the WAF commonly blocks default language UAs (`Python-urllib` → 403) while curl/Firefox UAs pass — set an explicit UA in every farm/bench tool, never the library default. **Benchmark before mass-minting** (user rule): run unique prompts (identical prompts hit a server-side cache and report ~10x inflated TPS), measure TTFT/TPS/RPM-parallel/concurrency/fail-rate on the model you actually want, then decide scale. A `429 model_concurrency` on a shared free pool is GLOBAL saturation — minting more keys does not fix it; switch model or wait.

And the account itself is rarely the product — once sign-in works, mint the provider's OAuth token pair via its device-code flow: `references/oauth-device-code-harvest.md`; the injection leg into the user's router is skill `9router-ops`. A fourth wall can sit AFTER registration on new-api/Veloera-family gateways: identity bind (custom Telegram-verification module — bot deep-link with a one-time expiring token, channel `membership_required`, one Telegram identity per account); `telegram_oauth:false` in the public `/api/status` flags does NOT rule it out, because the module is configured out-of-band — dump `/api/status` first, then probe `/api/user/register` bare and read the `message` (this family answers HTTP 200 with `success:false`, so never branch on the status code); full recipe: `references/new-api-family-recon.md`.

Depth on reversing better-auth/Next.js clients: see `references/better-auth-reversal.md`.
China-platform phone signups (SMS OTP) stack TWO captcha walls: a Tencent 天御 click-chars captcha gates the send-code button, then an Aliyun WAF slider can intercept the code-send API itself — full recipe (ddddocr positions + RapidOCR direct recognizer, WAF slider drag, telemetry backoff) in `references/cn-phone-signup-captcha.md`.
Turnstile gate where siteverify rejects every route-mode token as `failed`: pivot the solver to REAL-PAGE mode — `{type:"turnstile", real_page:true, sitekey (from unauthed config endpoint or the page), url: <a REAL SPA route where the widget renders>, proxy: pinned, timeout_s:150, post_fetch: the target API POST from the same browser session}` — the same-session submit carries cookies, cf_clearance, and exit IP, which is what defeats context binding. `url` must be a route that exists in the client bundle's route map (grep `path:` in the app chunk) — a 404-view URL never mounts the widget and times out regardless of timeout. Exact param schema: `/opt/captcha-solver/turnstile/solve.py`.
Free-tier SaaS signup whose dashboard masks the secret (Firecrawl: 1,000 credits/account, monthly reset): signup + CLI PKCE key extraction — see `references/firecrawl-free-tier-farm.md`; rotation helper `scripts/fc-farm.sh`; full-auto Playwright wrapper at `/opt/firecrawl-farm/firecrawl_farm.py` (commands `new|status|rotate|current`).
LLM API-provider targets (z.ai / GLM-5.3): signup, key page, verified endpoint map for OpenAI + Anthropic protocols, and the Aliyun-captcha signup recon incl. the unsolved verify wall — see `references/zai-glm-api-farm.md`.
Multi-model LLM gateway keys (opencode Zen and router-style aggregators): what a platform key unlocks, empirical model-classification ritual, and the tested free-tier snapshot — see `references/api-keys-vs-free-tier.md`.

## Infra wiring (order)
1. **Production farm repos live under `/opt/<name>`** — profile scratch cache is pruned after 24h; never park production there.
2. **Temp-email**: provider menu — mail.tm (public API fallback) vs self-hosted cloudflare_temp_email (preferred when the site password is known) — password discipline and the undelivered-verification-mail decision path in `references/temp-email-providers.md`. Self-hosted specifics: create the address with the site-wide header (`x-custom-auth`); read mails with the per-address JWT that call returns (`Authorization: Bearer`) — the site header 401s on mail reads. Mails list needs `?limit=&offset=`. Always send a browser UA (default urllib UA gets CF error 1010). **`POST /api/new_address` 403s on `x-custom-auth` alone** — send the full browser header set incl. `Origin`/`Referer` of the mail site (the API checks origin, not just the secret; mirror `_te_headers` in grok-farm farm.py). Generate HUMAN-LIKE mailbox locals, never random hex — the user's standing pattern is Vietnamese-style names (family+given+two-digit, e.g. `tmpdangmanh34@gyukopo.dev`); bot-grade locals are the first thing a provider's abuse filter eyeballs. Keep the configured `tmp` prefix in the local — on this temp-mail infra only prefixed locals receive mail.
3. **Captcha solver**: pass the SAME proxy to the solver request that the HTTP client uses — minting and spending must come from the same egress IP. For Turnstile-walled signups where the token is siteverified SERVER-SIDE: route-intercept tokens (`solved:true` in ~10s) get rejected by the target's API every time regardless of proxy pinning or action/cData — switch to real-page mode (`real_page:true` + `pre_actions` + `post_fetch` from the same browser session; the `post_fetch[0].status/body` from the target API is the only real success signal, and the response also harvests `cf_clearance`). Before invoking real-page, verify the form URL is a REAL router path: grep the main bundle's router map (`path:"/login"`) and query-param toggles (`?daftar=1`-style mode switches) — the obvious `/signup` URL can 404-render (no form → no widget → `checkbox clicked=False` → whole timeout burned). Get the sitekey from the target's unauthed config endpoint (`/api/auth/config` → `turnstile_site_key`) rather than scraping the DOM. Full mode decision table: solver lives in skill `captcha-solver-service`.
4. **Proxy pool**: sweep ports before each run; alive = an IP-echo request succeeds through the exact client stack (an HTTP 403 from the target = alive behind CF, a 000 = dead), and the sweep must be an HTTPS CONNECT through the client stack — some open ports on a proxy host are not CONNECT proxies and die mid-run with WRONG_VERSION_NUMBER. Ports die mid-run — switch to the next live line instead of retrying. Exit IPs are sticky per port per session, NOT rotating per connection. A Turnstile solve that clicks the checkbox then 408s is an IP-flag loop: rotating to a DIFFERENT port (new sticky exit IP) clears it; retrying the same port never does. In a browser-leg run, dead proxies surface as `title=Problem loading page` per leg — if the first ~4 legs all show that (with the odd "Just a moment..." being CF not route, which is fine), the pool is dead end-to-end: kill the run and re-sweep instead of letting it exhaust every remaining leg on known-dead exits. The run cannot produce accounts from a dead pool; stop early, refresh, relaunch.
5. Farm repo gets its own venv; standalone utility scripts stay stdlib-only.

## Auth-flow reversal from webpack chunks — do this BEFORE writing request code
- Scrape chunks with curl_cffi `impersonate='chrome131'` + proxy (plain curl is CF-blocked). Enumerate the chunk list from page HTML, fetch with a small thread pool, grep for route names, `signIn.`, `turnstile`, `createRequestToken`, `fetch(`.
- Read the AUTH CLIENT chunk (the one defining `createAuthClient`), not the UI chunk: it holds the base URL, the fetch helper, every route name, and the castle posture map.
- The real flow is often NOT the legacy gRPC/REST endpoint a vendored client targets — modern UIs migrate to JSON RPC or better-auth routes while old endpoints stay up, answering HTTP 200 with an EMPTY body. Repeated empty 200s = hunt for the replacement route in chunks before debugging payloads further.

## Verification strictness differs per endpoint — probe before choosing a token strategy
- Lenient verifiers (Next.js Server Actions, `next-action` header) accept route-intercept/stub solver tokens.
- Strict verifiers (better-auth sign-in, JSON `/api/rpc` anti-abuse) reject stub tokens with `anti-abuse:token-invalid` — no stub-URL variant fixes it; they verify the token was minted on the real page.
- For strict endpoints use solver realpage mode: `pre_actions` drive the live form, the natural token is harvested, and `post_fetch` spends it from the SAME browser session (same cookies/origin/proxy IP). Token shape lives in `captcha-solver-service`.
- Read error codes as LAYER probes: the progression `anti-abuse:token-invalid` → `account:invalid-credentials` means the anti-abuse layer PASSED — stop re-litigating token variants and move to credential reality.

## better-auth specifics
- Email/password sign-in: `POST /api/auth/sign-in` `{method:"email", email, password, turnstileToken, castleRequestToken?}`.
- OTP sign-in (no password): `POST /api/auth/send-verification-code` `{email, template:"email_code_login", flow:"login"}` — open posture, verified 200 `{"ok":true}` with NO castle and NO turnstile. Then sign in with `method:"email-code"` + the emailed code + turnstileToken (body shape from chunk reversal — confirm live before relying on it). Use this path when password credentials are suspect.
- A server-action "ok" response is NOT proof the account exists: small fixed-length RSC body + zero set-cookies across all accounts = silent failure. Verify by an authenticated call (e.g. send-verification-code or sign-in) before reporting accounts as created.

## Pitfalls
- Progressive forms: the password input mounts only after the email step's submit click — in solver pre_actions insert a submit click between the two fills, else element-not-found.
- Pages rendering Turnstile via the explicit JS API (`turnstile.render(el, {callback})`) keep the token OUT of the DOM — no `[name=cf-turnstile-response]` input exists; harvest must capture the render callback's token (hook injected before goto), with `window.turnstile.getResponse()` only as fallback. Alternative needing NO pre-goto hook: inject a SECOND `.cf-turnstile` div (fixed overlay) whose `data-callback` is a global fn that writes the token into a hidden `input[name=cf-turnstile-response]`, re-`turnstile.render()` it, then poll the input — defeats explicit-render widgets that keep their own token out of the DOM without touching page internals (pattern proven in proxyscrape signup solvers). proxyscrape signup = `https://dashboard.proxyscrape.com/v2/sign-up`, sitekey `0x4AAAAAAAFWUVCKyusT9T8r` — reuse this capture pattern (or the `:8877` solver real-page/same-proxy route) BEFORE writing a fresh click-through engine; plain interaction playback against explicit-render widgets burns sessions on a solved problem. Local engine dir `~/app/` (`ts_engine.py`, proxy lines in `proxies.txt`) exists if a standalone solver is wanted.
- OTP mail can arrive within seconds — poll the temp-email API on short intervals; a rate-limited send shows up as no mail for minutes, not an error. Parse the code from the mail SUBJECT, never the body (SPF-bounce text can carry a decoy XXX-XXX); regex + D1-direct reads + expiry/rate-limit windows: `references/better-auth-reversal.md`.
- Never echo credentials into logs or output; the farm repo's .env typically holds one password shared by all farmed accounts.
- Dashboard-masked secrets: when the provider UI masks the key in DOM, clipboard, and network responses, stop mining the UI after one confirming attempt — pivot to the provider's official CLI PKCE login, which writes the full key to a local credentials file. Recipe: `references/firecrawl-free-tier-farm.md`.
- GitHub autoreg is DataDome-walled: any datacenter-proxy exit hits 'Access is temporarily restricted' hard-block within ~30s of warm-up — a DC pool cannot farm GitHub, only residential/ISP exit IPs pass. The good farm tools already refuse the DIRECT home IP as a fallback; keep that guard — an IP-abuse-sensitive target burns the home IP against its own rate limiter.
- Third-party farm repos load `proxy_file` via `ROOT / <name>` (absolute paths silently miss) and parse each line with url-split requiring a scheme (raw `user:pass@host:port` fails validation) — both surface as 'proxy pool empty' + a 30-min replenisher stall, not an error. Copy the pool into the repo dir, set the RELATIVE filename, and prefix every line with `http://` / `socks5://`.

## Anti-bot recon rules (any target)
- Identify the anti-bot VENDOR from the frontend bundle before wiring the solver — grep the SPA chunk for `AliyunCaptchaConfig` / `turnstile.render` / `grecaptcha` / Castle init and match the solver `type` to the real widget. Secondhand docs mislabel vendors (z.ai is documented as Turnstile but ships Aliyun).
- Probe field types with deliberate type confusion before brute-forcing formats: send a dict where a string is expected → 422 Unprocessable Entity = pydantic string field. Read rejects by class: 422 = wrong shape, 400 = parsed but semantically rejected, 429 = parsed but throttled (per-email countdown shrinks per hit — wait it out or burn the email).
- Captcha tokens are single-use and bound to the solving context (IP/origin) — run the solver through the SAME egress that submits the form (solver `proxy` = signup egress), with the page referer spoofed to the target origin. In a BROWSER farm this mismatch masquerades as a form bug: a Turnstile-injection farm that fails every submit with a generic "form rejected/stuck" or a page-level `Browser verification failed` / `client is not authorized to call this resource` banner is almost certainly submitting a token solved from the VPS IP — pass the account's own proxy line into the solver call (normalise to `http://user:pass@host:port`) BEFORE blaming the browser stealth or rotating more proxies.
- Routes behind Aliyun WAF block the source IP after a handful of failed submits (405 + zh HTML) — move egress to a proxy BEFORE brute-forcing; once blocked, that IP stays blocked for the endpoint.
- Aliyun widget solver usage (self-hosted :8877, type `aliyun`): pass `skip_verify: true` when replaying the token at the target — the default flow self-verifies via T001 and the certifyId is SINGLE-USE, burned before the target can consume it. Direct CLI: `cd /opt/captcha-solver && venv/bin/python -m aliyun._run <scene_id> <prefix> <region> <timeout_s> <proxy> <skip_verify>` (run from repo cwd), success = `__ALIYUN_RESULT__{json}` stdout line. Token shapes: verifyType 2.0 = `captchaVerifyCallback` dict `{sceneId, certifyId, deviceToken, data}`; verifyType 3.0 / success fallback = STRING `btoa(JSON{certifyId,sceneId,isSign:true})` — normalize string|object and guard `json.loads` before use. `pre_actions` accept `soft: true` = log-and-skip on failure, for opportunistic clicks that shouldn't kill the run.
